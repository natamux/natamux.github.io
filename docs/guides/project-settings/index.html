Project settings

Each project has its own settings: the stages every task goes through, where task context comes from, the issue tracker and how agents ask for permission. Natamux keeps them in .natamux.json at the root of the repository, so you can commit the file and share it with your team.

Open them from the sidebar: click the gear next to the project. Or right-click the project, or click … next to it, and choose Settings. The screen is called Project settings of <repo> and has three tabs: Stages (the default), Issues and JSON.

The Stages tab

Section titled “The Stages tab”
  • Pipeline preview. A flow chart on top shows the stages as you edit them, with side-by-side stages in one column. A person icon marks a stage that waits for your approval. A pencil marks a prompt of your own. A stage on its own agent shows that agent’s icon and its model (or the agent’s name) under its name. Click a node to select its stage.
  • Stages in order. One row per stage, with a checkbox that turns it on or off, and a drag handle. Drag a row, or focus it and press Alt+ArrowUp or Alt+ArrowDown. The row menu has Move up, Move down, Run alongside the stage above, Run on its own and Remove. A stage that is off stays in the file with its prompt and approval, but new tasks do not get it.
  • Add stage opens the catalog of 28 stages, grouped by phase: Understand, Design, Build, Check and Ship. Custom stage makes a stage of your own. The catalog lists every stage.
  • Details. Click a stage to edit it.

  • Footer. Reset to default puts the default pipeline in the editor. Import… and Export load and save a file; see Import and export. Cancel closes the screen. Save (Mod+Enter) writes the file. A line above them, except on the Issues tab, says: “New tasks use this pipeline. Tasks on their way keep their stages, but use the new prompts and approvals.”

Save changes only stages. Other fields and keys it does not know stay in the file. When the stages equal the default pipeline, Save leaves stages out of the file, so the project follows later changes of the default.

The Issues tab

Section titled “The Issues tab”

The Issues tab sets when Natamux opens a GitHub issue for a task (tracker.createIssue). By default it opens none: Only when you click Create issue in the task’s Progress view. The other choices open the issue when you approve the Spec stage, or just before the pull request opens. Never also hides the Create issue button.

Under the choices, the tab says what the issue is made of. With tracker.type set to none, the choices are turned off. See Open an issue for a task.

The JSON tab

Section titled “The JSON tab”

The JSON tab edits the whole file as text. Edits move between the tabs. JSON that is not valid keeps you on this tab with the error shown, until you fix it. Use it for fields the Stages tab does not show:

  • requireCommit, requireClean and check on a stage;
  • context.sources, such as a skill or MCP source with a name of its own;
  • tracker.type and tracker.linkInPr, the rest of the issue tracker;
  • agents.permissionMode, auto or ask.

Every field is in the configuration reference.

Import and export

Section titled “Import and export”

Use these to copy settings from one project to another, or to keep a copy.

  • Export downloads what the screen shows, edits included, as <project>.natamux.json. It is turned off while the JSON tab holds JSON that is not valid.
  • Import… opens a .json file (up to 1 MiB) in the screen, in place of the current settings. When the file has a Check command, Command or Arguments on any stage, it asks first and lists each one, with its stage, in full: they run on this computer. With edits not saved, it asks too, in the same question. It does not save: check the settings, then click Save. A file with a problem opens on the JSON tab with the error.

To use an exported file in another project, import it there, or copy it into the repository as .natamux.json.

When the file changes

Section titled “When the file changes”
  • If the file changed on disk since you opened the screen (another editor, a pull), Natamux says “The file changed on disk since you opened it.” Reload reads the file again and drops your edits. Overwrite saves your version over it.
  • Closing the screen with edits asks “Discard your changes?”.
  • If the file is not valid, the screen shows the error and the default settings, and Save asks before it replaces the file.
  • The daemon reads the file again when it changes, so an edit in your own editor counts at once.

Common changes

Section titled “Common changes”

Choose the review agent

Section titled “Choose the review agent”
  1. Click Review in the stage list.
  2. In Agent, pick the agent, for example Codex.
  3. Optional: in Arguments, add words such as --model sonnet.
  4. Click Save.

Review runs in its own terminal, Terminal 5, so it can use another agent than the task’s without touching the session in Terminal 1. Test spec works the same way, in Terminal 2. See The review loop.

Split the pipeline by a condition

Section titled “Split the pipeline by a condition”
  1. Click Add branch and give it a Branch name.
  2. Give each path a Path name and a condition, such as File has text (a section of plan.md) or Command succeeds.
  3. Click Save.

See Paths with a condition and Build a workflow.

Give a stage another agent

Section titled “Give a stage another agent”

Click the stage and set Agent and Arguments. The stage then runs in its own terminal. See Mix agents in one task.

Have a person read the diff

Section titled “Have a person read the diff”

Click Add stage, pick Manual review in the Check phase, and drag it after Review. The task then waits for your Approve before Release. To make the agent review wait for you as well, tick Wait for my approval on Review.

Skip the planning

Section titled “Skip the planning”

Turn off Plan with its checkbox. After you approve the spec, Test spec and Implement start at once.

Add a check stage

Section titled “Add a check stage”

Pick Security review, Performance check or Accessibility check from the catalog. Each one writes a report with a Findings section and waits for your approval. Like Review, it runs in Terminal 5, the one terminal that all such stages share. When an agent still runs there, for example the Review agent, the stage gets its prompt in that session. With its own Agent or Arguments, it runs in a terminal of its own instead, from Terminal 6.

Run your own test command

Section titled “Run your own test command”

Click Automated tests and enter a Command, such as pnpm test. A terminal runs it instead of an agent. Exit code 0 passes the stage.

What a change does to tasks

Section titled “What a change does to tasks”
  • New tasks use the new pipeline.
  • A task on its way keeps its list of stages. It uses the new names, prompts, approvals and checks of those stages.
  • A catalog stage that is gone from the file keeps its catalog settings for a task on its way.
