Use cases

Start with the work you want to finish. Pick a case, choose where a person should approve it, then save the settings in your repository.

With a manual context source, Natamux writes context.md and passes Context automatically, even with "gate": "manual". The short flow starts Implement next. To approve the notes before coding, add a separate manual stage after Context. See Context sources.

Create settings with an agent

Ask an agent such as Claude to read this page first. Then describe your work and the stages you want. The agent can help you quickly create a .natamux.json settings file that fits your workflow.

The contents list links to each case and the four complete recipes below. For the building blocks, see Build a workflow and Stages.

Use a recipe

Section titled “Use a recipe”

Save one complete JSON example as .natamux.json at your repository root. Open the project’s Settings, then Stages to inspect the flow or JSON to edit the whole file. Save writes it back. Create a new task to use the new sequence. See Project settings for import, export and how changes affect existing tasks.

Before you start:

  • Install and sign in to the agent CLIs you choose. A stage without an agent uses the task’s agent. The recipes with Codex need Codex as well as the task’s agent.
  • Adapt test commands to your repository. The command recipes below assume Python 3 and a tests/ directory containing unittest tests. Approve repository commands in Project settings before running them.
  • For a Release stage, configure a GitHub remote and sign in to gh. Release pushes the branch and opens a pull request after approval. It does not deploy your service. See GitHub.
  • Commit the settings file to share the process. Each developer still has local tasks and workspaces. The file shares the sequence; it does not synchronize live task state or assign reviewer roles.

Parallel stages of one task share its worktree. Let one stage edit code while the other writes a separate report. Separate tasks and fan-out attempts have separate worktrees when you create their workspaces. More agents also need more memory and agent capacity.

Simple projects

Section titled “Simple projects”

First small change

Section titled “First small change”

For: someone trying Natamux on a small repository. Task: fix a button label. Choose this when you can describe the whole change in a few sentences.

Flow: Context → Implement → Manual review. Use the short flow. Context passes automatically and Implement starts next. You inspect the changed files at Manual review. The result is a small diff ready for your own commit. Next: create a task with the old and new label, then start it.

Documentation change

Section titled “Documentation change”

For: a maintainer updating installation steps. Task: replace an outdated command and check the surrounding links. A short flow keeps a prose change easy to review.

Flow: Context → Documentation → Manual review. Start from the short flow, then replace Implement with Documentation from the stage catalog. In the task, name the pages and the documentation build command; that tool must already be installed. You approve the instructions after reading the rendered page. Next: attach the incorrect instructions to a new task.

Personal website

Section titled “Personal website”

For: a developer maintaining a portfolio. Task: add a project card that works on a phone. Choose a visual check before accepting the diff.

Flow: Context → Implement → Manual testing → Manual review. Add Manual testing before the final stage of the short flow. Include the repository’s preview command in the task. The result is a card you can open locally. You check a narrow and a wide viewport before approving it. Next: supply the card text and a reference image you may publish.

CLI tool

Section titled “CLI tool”

For: a developer maintaining a small command line tool. Task: make an invalid option print a useful error and return a nonzero exit code.

Flow: Context → Implement → Automated tests → Manual review. Add Automated tests to the short flow, with the tool’s test command. The runtime and test dependencies must be available in the workspace. Expect a regression test and the corrected error. You try the command yourself before approving. Next: paste one failing invocation and its expected output into the task.

Solo work

Section titled “Solo work”

Bug fix

Section titled “Bug fix”

For: a solo maintainer fixing a reproducible defect. Task: correct a date calculation at the end of a month. Use a written spec to keep the edge cases visible.

Flow: Context → Spec → Implement → Agent review → Manual review. Use the agent review recipe. Expect a regression test, a fix and a review report. You approve the reproduction and final diff. Next: provide a failing date, expected result and test command.

New feature

Section titled “New feature”

For: a developer adding search to a notes app. Task: search titles with clear empty and loading states. Choose this when agreement on behavior matters before coding.

Flow: Context → Spec → UX design → Implement → Agent review → Manual review. Add UX design after Spec in the agent review recipe. The result includes a screen description and an implementation. You approve the behavior, then test the states in the running app. Next: list what search must match and what it must leave out.

Refactor

Section titled “Refactor”

For: a maintainer splitting a large module. Task: move parsing and formatting into separate files while preserving behavior.

Flow: Context → Spec → Refactor → Automated tests → Manual review. Adapt the short flow: add Spec, replace Implement with Refactor, and add Automated tests with your test command. Existing tests are a prerequisite. Expect smaller files and passing tests. You check that the diff contains the agreed changes only. Next: name the module and the public interfaces that must stay stable.

Test coverage

Section titled “Test coverage”

For: a developer protecting code that already works. Task: add tests for retry and timeout behavior without changing production code.

Flow: Context → Test spec → Implement → Automated tests → Manual review. Adapt the agent review recipe with Test spec and a test command; tell Implement to edit tests only. Expect a case list and runnable tests. You review whether the tests represent real failure modes. Next: list the behavior and the test harness to use.

Compare attempts

Section titled “Compare attempts”

For: a developer choosing between approaches. Task: try different implementations of a slow parser. Separate attempts let you compare measured results.

Flow: One task → Fan out → Compare diffs and measurements → Keep one try. Use Fan out with the same input and benchmark command for every attempt. Automatic fan-out launches Claude Code only; start other agents yourself on draft tries. Expect separate workspaces and candidate diffs. You choose the result using correctness and timings. Next: define a benchmark and run more tries before the original task finishes.

Independent review

Section titled “Independent review”

For: a developer who wants a fresh session to inspect a change. Task: review a patch against its accepted spec.

Flow: Context → Spec → Implement → Agent review → Manual review. Use the agent review recipe. Its review stage uses its own terminal, writes findings and sends work back when needed. A fresh session still needs clear acceptance criteria. You read the final report and diff. Next: set the review agent and start a task with a testable result.

Teams

Section titled “Teams”

Mix agents

Section titled “Mix agents”

For: a team that already uses more than one agent CLI. Task: let the task’s agent implement a change and Codex review it.

Flow: Context → Spec → Implement → Codex review → Manual review. Use the agent review recipe and install both agents. The review agent changes without replacing the task’s agent. Expect a diff and a separate report. A person makes the final decision. Next: pick the agents your team can run; see Mix agents in one task.

Parallel test planning

Section titled “Parallel test planning”

For: a team building a Python feature from an agreed spec. Task: implement a CSV export while another stage lists test cases without reading the implementation.

Flow: Context → Spec → [Test spec ‖ Implement] → Automated tests → Manual review → Release. Use the parallel team recipe. Python and the repository’s tests must be available. The report writer owns test-spec.md; Implement owns the code. Expect code, a case list and tests checked against it. You approve the spec, diff and pull request creation. Next: define the CSV format and error cases.

GitHub issue

Section titled “GitHub issue”

For: a maintainer taking work from an issue queue. Task: implement an accepted issue with its discussion kept as context.

Flow: Import issue → Context → Spec → Implement → Review → Release. Use the parallel team recipe, or the default pipeline for a smaller issue. Keep github-issue in context.sources; GitHub access and gh are required. Expect the issue context and a linked pull request. You check that the scope matches the discussion before implementation. Next: import one issue through the GitHub guide.

CI retry

Section titled “CI retry”

For: a team with a CI workflow on GitHub. Task: fix an export change that passes locally but fails on a supported Python version in CI.

Flow: Context → Spec → Implement with Check on CI → Failed logs → Implement again → Manual review. On Implement in the parallel team recipe, set ci to true, then enable Check on CI for the task. GitHub access and configured CI workflows are required. Natamux pushes a snapshot for the check and can send failed logs back. The recipe sets agents.maxSendBacks to 2; past that limit, you decide what to do. Next: select the CI option before starting that stage; see Check a stage on CI.

Larger organizations

Section titled “Larger organizations”

Conditional routing

Section titled “Conditional routing”

For: maintainers of a repository with both small fixes and larger features. Task: give a bug a short path and a feature a written plan before implementation.

Flow: Context → Triage → [Bug path or Feature path] → Automated tests → QA → Release. Use the organization recipe. You approve the Triage report before the condition runs. A report containing bug in its Route section takes the first path; otherwise the feature path runs. Expect one chosen path, test results and a reviewable diff. Next: describe the change and check the route before approval.

Shared settings and human approvals

Section titled “Shared settings and human approvals”

For: a larger engineering group that wants the same steps in each local checkout. Task: change an account settings screen with explicit acceptance and QA decisions.

Flow: Context → Triage → Conditional work → Tests → QA → Release. Commit the organization recipe, then adapt it through code review. Python, tests and GitHub access are prerequisites. People agree outside Natamux who reviews the work; a local gate does not enforce a team role. Expect the same configured process for new tasks on each machine. Next: agree on the gates, commit the file and let each developer install their own agents.

Security-sensitive change

Section titled “Security-sensitive change”

For: a team changing an access check. Task: reject an unauthorized request while preserving authorized behavior.

Flow: Context → Spec → Threat model → Implement → Security review → Manual review → Release. Add the Threat model and Security review catalog stages to the agent review recipe, then add Release if you use GitHub. Expect threat notes, tests and findings for a person to inspect. Review prompts alone do not establish a secure result or certification. Next: name the protected resource and expected allow and deny cases, using synthetic data.

Performance-sensitive change

Section titled “Performance-sensitive change”

For: maintainers of a service with a slow path. Task: reduce repeated parsing without changing the result.

Flow: Context → Spec → Implement → Performance check → Manual review. Add Performance check to the agent review recipe. Supply a reproducible benchmark and the required runtime. Expect before and after measurements alongside tests. You decide whether the improvement justifies the change. Next: agree on the input size and acceptable timing before implementation.

Complete settings recipes

Section titled “Complete settings recipes”

Each block below is a complete project file. Fields left out use the defaults. These examples use ordinary repository tools and public Natamux settings. Read the configuration reference before adding conditions, commands or agent arguments of your own.

Recipe: short flow

Section titled “Recipe: short flow”

For a small local change. It uses manual context only and does not open GitHub issues or pull requests. You commit after reviewing the result.

Complete file: .natamux.json

Recipe: agent review

Section titled “Recipe: agent review”

For a solo change with a spec and a second opinion. Install Codex for the review stage, or change agent to an installed agent. The task’s own agent implements the work. The two-send-back limit is explicit.

Complete file: .natamux.json

After a send back, the earlier stage runs again. The reviewer must stop instead of marking the old stage done. See The review loop.

Recipe: parallel team

Section titled “Recipe: parallel team”

For a Python repository where implementation and test planning can run together. Install Codex, Python 3 and the project’s dependencies. Adapt python3 -m unittest discover -s tests if your suite uses another runner. Sign in to gh before Release.

Complete file: .natamux.json

The command stage runs after both parallel stages and the case check finish. Exit code zero passes it. A person reviews the diff and commits it before approving Release. For a longer solo and team walkthrough, see Build a workflow.

Recipe: organization

Section titled “Recipe: organization”

For a Python repository with an approved route and a QA gate. This example uses manual task context, Python tests and GitHub pull requests. Adapt the prompts and command before starting. permissionMode: "ask" leaves each agent’s own permission settings in control; it does not define a new permission policy.

Complete file: .natamux.json

Read the Triage report before approving it. Only the chosen path runs. After the tests pass, the manual testing gate is your place to try the accepted cases and inspect the diff. Commit approved work before approving Release. Use your GitHub branch rules for pull request review requirements; Natamux’s local approvals do not replace them.
